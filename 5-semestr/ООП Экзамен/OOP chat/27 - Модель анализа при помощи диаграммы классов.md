## Модель анализа (через диаграмму классов)

### Что это

Модель анализа — это **набор диаграмм классов**, которые показывают, **как будут реализованы прецеденты** (Use Case), но **без привязки к коду**.

Это шаг **между требованиями и проектированием**.

---

### Зачем нужна

* понять, **как система будет работать внутри**
* проверить требования на реализуемость
* заложить основу **архитектуры и декомпозиции**

---

### Чем отличается от модели предметной области

* предметная область → *что существует в реальном мире*
* модель анализа → *как система будет это обрабатывать*

---

## Стереотипы классов в модели анализа

Используются **3 основных стереотипа**:

### 1. **Boundary (граничный класс)**

* взаимодействует с актёрами
* формы, экраны, API
* принимает ввод / показывает вывод

👉 «точка входа в систему» - 
# Круг и буква Т слева

---

### 2. **Control (управление)**

* координирует выполнение прецедента
* содержит бизнес-логику сценария
* управляет вызовами других классов

👉 «мозг процесса»

# Круг и касательная стрелка влево сверху

---

### 3. **Entity (сущность)**

* хранит данные
* обычно соответствует таблицам БД
* долго живёт

👉 «данные системы»

# Круг и Т снизу
---

## Создание модели анализа

1. Для каждого **Use Case** строится диаграмма классов
2. На диаграмме используются **Boundary / Control / Entity**
3. Классы связываются между собой
4. После этого выполняется **декомпозиция на пакеты**

---

## Пакеты анализа (важно)

⚠️ **Пакет “управление” ≠ стереотип Control**

Пакеты — это **логическое разбиение системы**, например:

* управление регистрацией
* управление каталогом
* управление заказами
* сервисные функции (почта, уведомления)

Каждый пакет:

* отвечает за **одну подсистему**
* содержит свои boundary / control / entity классы


# Отображаются как прямоугольник с прямоугольников вверхнем левом углу
---

## Кратко для запоминания

* модель анализа = реализация прецедентов
* ещё не код
* 3 стереотипа: **Boundary / Control / Entity**
* основа архитектуры и декомпозиции
