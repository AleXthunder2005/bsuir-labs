## 10. Понятие IRP-пакета. Схема обработка IRP стеком драйверов.

Отлично! Давай разберём билет **10** про **IRP (Input-Output Request Packet)** и его обработку **простым языком** с примерами. Я сохраню все детали, но объясню их доступно.

---

## **1. Что такое IRP-пакет**

IRP — это «заявка на ввод-вывод».

Проще говоря:

> Когда программа хочет прочитать файл, записать данные на диск или отправить что-то на устройство, Windows формирует **IRP-пакет** — конверт с информацией о запросе, который передаётся драйверам для обработки.

**Пример:**

* Программа вызывает `ReadFile()`.
* Менеджер ввода-вывода создаёт IRP, в котором указано:

  * какой файл читаем (`FILE_OBJECT`),
  * куда положить данные (`UserBuffer`),
  * какой драйвер должен обработать запрос.

---

## **2. Структура IRP**

IRP состоит из нескольких частей:

1. **Фиксированная часть** — общая информация, которая есть у любого IRP.
2. **Стек драйверов (IO_STACK_LOCATION)** — для каждого драйвера в цепочке есть «свой конверт внутри конверта». Каждый драйвер читает свою запись, делает свою работу и передаёт пакет дальше.

   * `StackCount` — количество драйверов, через которые пройдёт пакет.
3. **FILE_OBJECT** — файл или устройство, с которым работает пакет.
4. **Буферы данных**:

   * `UserBuffer` — данные в памяти пользователя,
   * `SystemBuffer` — данные в системной памяти.
5. **MDL (Memory Descriptor List)** — карта памяти для передачи данных между пользовательским и системным режимом.
6. **Поток (ETHREAD)** — указатель на поток, который отправил запрос, для управления очередью IRP.

---

## **3. Алгоритм обработки IRP при открытии файла (простыми словами)**

Представим, что **пользователь хочет открыть файл `C:\file.txt`**:

### **Шаги:**

1. **Программа просит ОС открыть файл**

   * Вызов `CreateFile()` в пользовательской программе.
   * Подсистема Win32 обращается к **менеджеру ввода-вывода** (I/O Manager).

2. **Создаётся объект файла (FILE_OBJECT)**

   * Менеджер объектов проверяет права пользователя.
   * Если диск ещё не смонтирован, сначала монтируется том.

3. **Менеджер создаёт IRP**

   * Выделяет память через `IoAllocateIrp()`.
   * В IRP создаётся **IO_STACK_LOCATION** для верхнего драйвера в цепочке.

4. **Вызов верхнего драйвера**

   * Менеджер вызывает `XxxDispatchCreate()` верхнего драйвера (например, драйвер файловой системы NTFS).
   * Драйвер проверяет, нужно ли использовать кэш.
   * Если пакет должен идти дальше, драйвер копирует стек для следующего драйвера (`IoCopyCurrentIrpStackLocationToNext()`) и регистрирует **CompletionRoutine** (`IoSetCompletionRoutine()`), чтобы узнать, когда пакет обработан.
   * Вызывает следующий драйвер через `IoCallDriver()`.

5. **Каждый драйвер в цепочке выполняет свою работу**

   * Например:

     * Драйвер файловой системы NTFS формирует данные для чтения.
     * Драйвер нижнего уровня (Bus Driver / Device Driver) взаимодействует с физическим устройством (жёсткий диск, SSD).

6. **Драйвер устройства обрабатывает запрос асинхронно**

   * Драйвер помечает IRP как **ожидающий обработки** (`IoMarkIrpPending()`) и ставит его в очередь к устройству.
   * Когда устройство готово, вызывается **ISR (Interrupt Service Routine)**, которая запускает DPC-процедуру через `IoRequestDpc()`.

7. **DPC-процедура выполняет ввод-вывод**

   * Извлекает IRP из очереди (`IoStartNextPacket()`), выполняет операцию и устанавливает статус (`IoStatus`).
   * Вызывает `IoCompleteRequest()`, чтобы уведомить драйверы о завершении.

8. **Процедуры завершения (CompletionRoutine)**

   * Каждый драйвер в стеке получает уведомление (`XxxIoCompletion()`).
   * Проверяет статус: если ошибка, можно повторить операцию или завершить.
   * IRP возвращается менеджеру ввода-вывода.

9. **Менеджер ввода-вывода завершает обработку**

   * Копирует результат в адресное пространство программы (NTSTATUS).
   * Освобождает IRP через `IoFreeIrp()`.
   * Программа получает описатель файла, готовый к чтению/записи.

---

### **Пример с аналогией почтового конверта**

* IRP — это конверт с письмом.
* В конверте есть **несколько вложенных конвертов (IO_STACK_LOCATION)**: для каждого драйвера в цепочке.
* Конверт идёт по цепочке:

  1. Файловая система
  2. Фильтрующий драйвер
  3. Драйвер устройства
* Каждый драйвер делает свою часть работы и передаёт конверт дальше.
* Когда конверт дошёл до конца, все вложенные конверты раскрываются в обратном порядке, уведомляя драйверы о результате.

---

💡 **Главная идея:**

IRP позволяет ОС Windows реализовать **многоуровневую асинхронную модель ввода-вывода**:

* Все драйверы работают в своей «ячейке» IRP (IO_STACK_LOCATION).
* Драйверы могут работать одновременно, не блокируя друг друга.
* Менеджер ввода-вывода координирует весь процесс и возвращает результат пользователю.

---

## **2. Как выглядит IO_STACK_LOCATION в программе**

На уровне кода это **структура в C**, примерно так (упрощённо):

```c
typedef struct _IO_STACK_LOCATION {
    UCHAR MajorFunction;      // Тип операции: IRP_MJ_READ, IRP_MJ_WRITE, IRP_MJ_CREATE и т.д.
    UCHAR MinorFunction;      // Подтип операции
    PDEVICE_OBJECT DeviceObject;  // На какое устройство направлен запрос
    PFILE_OBJECT FileObject;      // Файл или устройство, с которым работает драйвер
    PVOID Parameters;             // Параметры операции (смещение, размер буфера и т.д.)
    PVOID CompletionRoutine;      // Функция, которая вызовется при завершении
    PVOID Context;                // Контекст для CompletionRoutine
} IO_STACK_LOCATION, *PIO_STACK_LOCATION;
```

То есть **IO_STACK_LOCATION — это кусок памяти внутри IRP**, где драйвер хранит всё, что нужно ему для обработки запроса:

* какой тип операции,
* к какому устройству/файлу обращаемся,
* где буфер данных,
* куда сообщить о завершении операции.

## **3. Пример на практике**

Представим простую операцию: **чтение файла `C:\file.txt`**

1. Программа вызывает `ReadFile()`.

2. Менеджер ввода-вывода создаёт IRP с **массивом IO_STACK_LOCATION**, размер которого = количество драйверов в цепочке (StackCount).

   * Верхний драйвер — драйвер файловой системы NTFS → получает IO_STACK_LOCATION[0]
   * Следующий драйвер — фильтрующий драйвер → IO_STACK_LOCATION[1]
   * Драйвер устройства (диск) → IO_STACK_LOCATION[2]

3. Каждый драйвер смотрит **только на свою IO_STACK_LOCATION**:

```c
PIO_STACK_LOCATION stack = IoGetCurrentIrpStackLocation(Irp);
if (stack->MajorFunction == IRP_MJ_READ) {
    // читаем данные из DeviceObject
    // после завершения вызываем stack->CompletionRoutine
}
```

То есть **IO_STACK_LOCATION — это интерфейс драйвера с IRP**, чтобы он знал, что делать с этим конкретным запросом.

---

## **4. Как это выглядит в памяти IRP**

```
IRP (конверт)
├─ IO_STACK_LOCATION[0] -> для файловой системы NTFS
├─ IO_STACK_LOCATION[1] -> для фильтрующего драйвера
└─ IO_STACK_LOCATION[2] -> для драйвера устройства (диск)
```

Когда IRP идёт вниз по стеку драйверов:

* Каждый драйвер смотрит **свою карточку**
* Делаем нужное действие (чтение, запись, открытие)
* Передаём IRP дальше

Когда IRP идёт обратно:

* Каждый драйвер вызывается через **CompletionRoutine**, чтобы обработать результат.
